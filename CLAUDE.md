# Nuke Wars — Project Instructions

## What this project is
A 1v1 web-based strategy game: simultaneous hidden orders, hex-grid maneuver, drone reconnaissance, fully deterministic combat (no dice — dread comes from hidden information), and a hidden-bunker decapitation endgame ("commit → dread → reveal" is the core loop).

**The full game design is in `docs/nuke-wars-v1-spec.md`. Read it before implementing any game rule, and treat it as the source of truth for all mechanics, numbers, and V1 scope.** If an implementation decision would change a rule or number in the spec, say so explicitly and update the spec file as part of the change.

**The design was pivoted on 2026-08-11** (single missile type, unlimited munitions, recon drone, decoy bunker, per-round intercept cap, hits-based damage, deterministic combat). The spec is fully post-pivot; spec section *numbers* §1–§9 kept their old meanings so code citations stay valid, and §10–§12 are new. **But §8's build-order step numbers changed** — old step 2 was "simulation engine core"; new step 2 is the pivot migration. Existing code comments citing "build-order step 2" mean the old numbering; fix them as you touch each file. Systems cut in the pivot (and the decoy, promoted back in) are listed at the top of `docs/v2-backlog.md`.

`docs/v2-backlog.md` is deferred-feature reference only — never implement from it. Its "Considered and set aside" section (bunker repair, dug-in launchers, hold fire) holds **optional** ideas, not V2 work items: one is built only if the designer explicitly picks it. `docs/v1.1-design-consultation.md` and `docs/v2-gameplay-analysis.md` are **closed** history as of 2026-09-28; nothing more is to be built from either.

**The rules layer is FROZEN as of 2026-09-28** (spec §8). `src/sim/` changes only for bugs. A rules change needs the designer to explicitly reopen the freeze, usually because of something found in a human playtest, and never happens as a side effect of presentation work. Current work is V1.5 (cosmetics first, then networking): see "Next up" and `docs/roadmap-v1.5.md`.

## Stack
- TypeScript + Vite + React 19
- PixiJS v8 for the game map/rendering
- Zustand for client state
- Hex math is hand-rolled in `src/sim/hex.ts` (axial coords) — deliberately dependency-free so the sim engine can move server-side unchanged in V1.5
- Hosting: static client on Vercel (auto-deploys `main`; see `docs/deploy.md`). CI: GitHub Actions (`.github/workflows/ci.yml`)
- Later (V1.5 Sessions 5–8, `docs/roadmap-v1.5.md`): Node.js WebSocket server on Railway (not yet in the project)

## Architecture rules (non-negotiable)
- `src/sim/` — pure simulation engine. NEVER import React, Pixi, DOM APIs, or anything network-related here. All game rules, state, and resolution live here as pure functions.
- `src/state/` — client state (Zustand). **The only module that ever holds an unfiltered `GameState`**, in a module-private variable with no accessor, so `src/render/` and `src/ui/` are structurally incapable of seeing the truth (spec §6 layer 2). May import `src/sim/`; `src/sim/` may never import it. React lives only in `state/useMatch.ts` — the store itself is a plain testable object.
- `src/render/` — PixiJS drawing only. Reads state, draws it. Never mutates game state. The type flowing in is `VisibleGameState` and nothing else.
- `src/ui/` — React HUD/menus. Same rule: reads state, sends player intents.
- **V1 combat is deterministic BY DESIGN — `resolve()` uses no randomness at all.** The seeded RNG (`makeRng` in `src/sim/map.ts`) is used only for map generation. `resolve()` keeps a `seed` parameter for forward compatibility but nothing in V1 resolution may read it (documented in spec §6 — don't "fix" this by adding RNG). No `Math.random()` anywhere in sim code, ever. Every simultaneous tie has a written tiebreak in the spec (§10); determinism bugs are iteration-order bugs.
- Game stats/definitions (units, terrain, rule numbers) go in plain data tables keyed by string IDs in `src/sim/defs.ts`, not hardcoded logic branches.
- Combat/resolution animates from the emitted event log, not by diffing states. Event visibility (which player may see which event) is specified in spec §6 — respect it in the visibility filter, never in resolve().
- **`resolve()` never lies; the visibility filter does.** The decoy bunker must be indistinguishable from the real one to the enemy, but the sim always stores and emits the truth (`kind: 'decoy'`). The decoy→bunker mask is applied *only* in `filterForPlayer`/`filterEventsForPlayer` (spec §6, §12). The visibility filter is the single place in the codebase permitted to know a decoy is a decoy.
- **Detection rules (spec §11) — four rules, no exceptions.** (1) The map is public and your own assets are always visible. (2) An enemy asset appears on your map only via one of exactly two detectors: the recon drone's swath, or automatic launch detection. (3) A launcher sighting lasts **one round** (the next order phase, then it's cleared — it can relocate); a static sighting (bunker, decoy, interceptor base) is **permanent** until public destruction. (4) No detection distinguishes the real bunker from the decoy. There is no vision radius around units, no line of sight, and no persistent "last seen" ghost markers — that history lives in the event log, which is permanent.
- **The indistinguishability principle (spec §12):** every rule that mentions the bunker must apply identically to the decoy, with hit points the only exception. Any asymmetry becomes a rules-derived tell that identifies the real bunker for free. When writing a new rule that touches the bunker, ask whether it must also name the decoy — the default answer is yes.

**Gotchas for future sessions — each of these is load-bearing, don't "simplify" any of them:**
1. The decoy is immobile and **blocks hexes** exactly like any ground unit. If it were passable, walking a launcher through a site would identify the fake for free.
2. The decoy never emits `BUNKER_HIT` — it dies to the hit. That silence-vs-destruction difference *is* the tell that identifies the real bunker. (The code's branch deliberately names bunker **and** decoy, so §12's "raise the decoy to 2 HP" lever stays symmetric by construction; at 1 HP the decoy can never reach it.)
3. Destroying a decoy triggers no dead hand and satisfies no win condition.
4. **Hits stack within a round** (spec §3): two missiles on a full-health real bunker kill it outright, so the impact phase must total damage per hex, not apply one hit per hex.
5. **`IMPACT` fires even when the target hex is empty** (spec §6). If it only fired on hitting something, its presence would leak occupancy and blind-fire probing would locate bunkers and bases for free.
6. **The dead-hand round is launches only** (spec §3): phases 2→3 only, no recon phase, no movement phase, no orders from the opponent. Since flight time (2026-09-27) phases 2→3 **repeat** until nothing is left in the air — see gotcha 65.
7. **Terrain is public** (spec §11). Hidden information covers assets, never tiles — the visibility filter must never strip or mask `MapData`.
7b. **`groundPassable` is not "can this be built here", and a mountain never shields the hex it stands on** (spec §2, §10, §12). V1 has two terrains. Mountains block launcher movement and — since 2026-09-28 — **line of fire**, but bunker, decoy and interceptor base may all be built on them. Placement validation must read `RULES.placementTerrain`, never `TerrainDef.groundPassable` — the field was renamed from `passable` precisely so that mistake looks wrong. Line of fire reads `TerrainDef.blocksFire` through `lineOfFireClear` (map.ts) and is **interior-only: `hexLine(origin, target).slice(1, -1)`**. That slice is the whole mountain-bunker argument. The rule this gotcha used to state — "missile targeting and flight never filter by terrain" — existed because a mountain site must stay hittable, and it is now the reason the exemption is exactly the target hex. Include the target (`slice(1)`) and every mountain site becomes invulnerable; filter `launchTargets` or the CPU's candidate hexes by the target's terrain and you do the same thing from the UI side. The one remaining way to wall a site in — ridges on every side — is closed by the generator (`NO_FIRING_LANE`, gotcha 7c), not by the rule. Flight never reads terrain: the check is at launch, in `validateLaunch`, and nowhere in `flyMissiles`.
7c. **`generateMap` validates and re-rolls; never patch a bad map.** Mountains are grown as ranges, and unlike scattered noise a ridge can wall the board off, so every generated map is checked for coverage, spawn connectivity, approach cost and — since line of fire — a firing lane to every home-zone hex from ground the spawns can reach (`NO_FIRING_LANE`, spec §7). That last rule re-rolls about 1 raw map in 4, so **any seed-pinned board changed on 2026-09-28**; a test that hard-codes "3 hexes north is a legal shot" on a generated map will break on some seed — read targets from `launchTargets` instead. Carving a pass through an offending ridge is the tempting fix and it is a trap — every carve must be applied to a hex *and its half-turn twin* or the two players silently get different maps.
8. **Launcher sightings expire after one order phase; static sightings never do** (spec §11). The intel state therefore has two parts with different lifetimes: a permanent set of revealed static assets, and a this-round-only set of launcher contacts that is rebuilt from scratch every resolution. Don't "improve" this by keeping stale launcher markers with a round number — persistent ghosts were deliberately cut; the event log is the history.
9. **The event log is append-only and permanent** (spec §6). Every launch a player detected stays readable for the whole match. Expiring a map marker must never delete a log entry.
10. **`UNIT_DEFS.drone.movement` is a straight-line flight range, not a ground budget** (spec §11). Never feed the drone to the ground-movement flood fill — it ignores terrain and units entirely. `reachableHexes` returns only its own hex for a drone and `validateMove` rejects drone MOVE orders with `AIR_UNIT`; the drone moves by FLY, resolved with `hexLine`.
11. **The board is fought north/south and its width MUST stay even** (spec §7). Territory splits by *row*: P1 south (rows 13–18, high numbers, advancing north), P2 north (rows 0–5). Hexes are flat-top precisely so the advance axis has true N/S neighbours. Map symmetry is a **180° rotation, not a mirror** — on flat-top odd-q hexes a top/bottom mirror shears the grid and hands the two players subtly different distances, and the half-turn is only an isometry while the width is even (hence 16, not 15). `generateMap` throws on an odd width and `map.test.ts` checks distance preservation over every hex pair. Consequence to expect, not "fix": the two sides' launcher *columns* differ (P1 col 2 answers P2 col 13).
12. **`hexLine` includes both endpoints, and the two callers slice it differently** (spec §10, §11). A missile checks for interception on every hex *after* the origin — `slice(1)`, keeping the target hex — while the drone's reveal swath covers the **whole** array including its start hex. Getting this backwards makes launchers shoot themselves down or blinds the drone to where it took off from. Never re-derive a line anywhere else (UI preview included) — call `hexLine`, or the pinned epsilon stops guaranteeing anything.

13. **`MOVE_FAILED` fires for exactly two rejection reasons — `TILE_OCCUPIED` and `OUT_OF_RANGE`** (spec §9). Every other rejection is dropped silently. This looks like an inconsistency worth "tidying up" and is not: `MOVE_FAILED` names a unit id, so answering an order that named an *enemy* unit would put a real enemy id into the sender's log — the trackable identity §11 exists to withhold. Once that case must be silent, reporting the other impossible-for-an-honest-client cases only makes "your advance met resistance" ambiguous between real contact and a UI bug. The two reported reasons are exactly the ones hidden information can cause.
14. **Movement events are emitted in `GameState.units` order, never order-array order** (spec §9). Both are deterministic, but only the canonical one makes the same physical outcome produce the same log no matter how a client sorted its submission — which is what the §6 determinism test is actually asserting. `resolve.test.ts` submits orders b-then-a and expects the log a-then-b; that test is the guard.
15. **`ordersPerUnit` is counted across ALL order kinds, not just MOVEs** (spec §3, §9). That is what makes move-XOR-launch structural — a launcher handed a MOVE *and* a LAUNCH is over budget and does nothing. Counting only MOVEs would look correct today and silently let that pair through the moment step 6 implements launches. An over-budget unit holds and emits nothing; the engine never guesses which order was meant. The budget is now applied **once** at the top of `resolve()` and the resulting `OrderBook` is shared by every phase — never re-derive it per phase, or a unit could be over budget in one phase and not another.

16. **`DroneFlight.path` is what the drone TRANSMITTED, not where it flew** (spec §11). On a downed flight it stops one hex short of the kill, and the death hex arrives separately in `DRONE_DOWNED`. This is why the reveal swath can be built from `path` with no special case — the "a shot-down drone reveals nothing from its death hex" rule is baked into the data rather than left to each caller. Note what it does *not* mean: the death hex itself is still spotted, from the corridor of the last hex the drone safely reached. What is lost is everything beyond it.

17. **A hovering drone still watches, and a rejected FLY is silent** (spec §11). No order, an invalid order and an over-budget order all resolve identically — a zero-length flight that transmits its own hex's corridor. Do not "tidy" this into an early `continue` that skips the swath: it would make hovering strictly worthless and quietly delete the reveal a player gets simply by having a drone alive. There is deliberately no air-layer `MOVE_FAILED`, because every FLY rejection is derivable from public or own-side information.

18. **The drone never blocks ground movement** (spec §2, §9). `occupiedHexes` skips `kind === 'drone'`, and that line is load-bearing: a drone that blocked would be a third detector by the back door — park it on a hex, watch an enemy launcher's advance fail, and you have located a unit no rule permits you to see. This was an actual bug fixed in step 5; it looked harmless for two build steps because drones never moved.

19. **The respawn tick is NOT one of §3's five phases** (spec §11). It runs as the resolution hands over to the next order phase, which is exactly what makes the delay count come out right (at `droneRespawnDelay` 1, since 2026-09-28: downed in round N, orderable in round N+1, with no blind round) *and* what puts the replacement drone on the board in time for the player to give it an order. Moving it to the top of `resolve()` would look equivalent and would silently cost the player a round: the drone would exist during resolution but never during an order phase.

20. **Recon can never photograph an interceptor base at the shipped radii, and that is the design** (spec §11, decided 2026-08-11; still true after the 2026-09-27 redesign, with a hex to spare). `reconSwathRadius` (1) ≤ `interceptorCoverageRadius` (2) means any base near enough to enter the swath is covering a hex the drone must enter to see it, so the drone always dies one step early — brute-force verified, not a hunch. Bases are found by inference from `DRONE_DOWNED`, or by exposure once one intercepts a missile (gotcha 64). Changing either radius is a board-wide balance change for playtest, not a fix; read the notes on both constants in `defs.ts` first.

21. **Owner-only events carry `owner`, and `ASSET_SPOTTED` is the trap** (spec §6). The visibility filter is handed the log and a player id and nothing else, so it cannot look a `unitId` up in a state to learn whose event it is — the audience must be on the event. Any new owner-only event needs an `owner` field or step 8 cannot route it. **But `ASSET_SPOTTED.owner` is the owner of the asset that was *seen*, so its audience is that player's opponent.** It is the single event where reading `owner` as "who may see this" is exactly backwards, and it is the one place a plausible-looking filter written from the pattern will silently show each player their own assets and hide the enemy's.

21b. **`LAUNCH_DETECTED` marks the DEFENDER's map — `intel[opponentOf(missile.owner)]`** (spec §11). Same trap family as 21: intel is keyed by the *viewer*, so `intel.p1` is what p1 knows about p2. Filing a launch contact against the firer would give each player a map of their own launches and hide the enemy's — and it would look perfectly reasonable in the diff, because `missile.owner` is right there. The rule to hold onto: nothing a player does ever writes to their own intel.

22. **The simultaneous-missile tiebreak is the ORIGIN HEX, never the launcher's unit id** (spec §10, changed in step 6). Ordering by id is just as deterministic and was the original wording — but the order is publicly observable, so it would leak an ordering of enemy launcher ids and, over a few rounds, let the defender track a specific launcher across the match. That is the trackable identity §11 keys every pile of intel by hex to withhold, and §6 already bans it for missile ids. `compareHex` exists for exactly this. **Bases keep the id tiebreak** (`basesCovering`), because the defender owns them, no event names one, and a base cannot move — so there is no identity to track.

23. **A base is self-protecting: one missile aimed at a base is always intercepted** (spec §10). A missile must cross a base's own bubble to reach it, so killing a base takes a **saturating volley of 2+ in one round**. This is the cap's whole purpose, not a bug — if a test or a UI hint assumes one missile kills a base, the test is wrong. (This bit during step 6: a test fixture had a lone missile "destroy" a base and the engine correctly ate it.)

24. **Interception advances every missile one step at a time, together** (spec §10). A base spends its single intercept on whichever missile *enters* its coverage first, so a missile two hexes out cannot be saved by one that would only have arrived later. Resolving one whole flight at a time looks equivalent and silently awards the intercept to whichever missile the array happened to list first — nondeterminism by array order, which is the exact class of bug §6 is guarding against.

25. **Phase 3 skips drones and corpses** (spec §2, §3). Missiles cannot touch a drone even when it is hovering directly over the target hex — the air layer is absolute — and an already-destroyed unit takes no second hit. Damage is totalled per *hex* before anything is applied, because the missile is aimed at ground, not at a target: whatever is standing there takes it, friendly or enemy.

26. **A round that ends at phase 4 stops there — no movement, no respawn tick** (spec §3, amended in step 7). §3 said this of dead hand only; it now applies to any verdict. It changes no outcome (nothing in movement can affect a §4 condition) and it is not tidiness: the log is what clients animate, so units moving after `GAME_OVER` would be a match that visibly carries on past its own ending. The rule players feel is that **the round which decapitates someone is a round in which nobody moves** — you cannot drive out of the dead-hand volley you just provoked.

27. **`adjudicate` reads `state.phase`, and that is the whole dead-hand distinction** (spec §4). One destroyed bunker means DEAD_HAND in a normal round and DECAPITATION in the final one — the *same board*. Do not "simplify" this into a boolean parameter threaded from resolve(): the state machine's current node is the fact, and a flag is a fact that can be passed wrongly.

28. **Absence is not destruction** (spec §4, ruled in step 7). A side with no bunker unit is not decapitated; a side with no launcher units is not disarmed. `startMatch` guarantees a real match never hits either case, so this exists to keep the engine inert on partial test boards — which is load-bearing in practice: without it, most of the 335 tests would end their match at phase 4 before reaching what they were testing. If you ever build a fixture where one side's only launcher is a corpse, that board is a disarmament and the round will stop; `resolve.test.ts`'s `spare()` helper is the fix.

29. **The dead-hand round gets its own round number; a finished match does not** (spec §3, §6). Dead hand increments because missile ids are `r{round}@{origin}` and the log keeps both rounds forever — reuse would collide. Game over freezes the counter, because `round` means "the round being played" and none is. Both are deliberate, and they are different on purpose.

30. **Placement validation must never look at the opponent's setup** (spec §12). It has no parameter for it, and that is the design: the home zones are disjoint (§7) so there is nothing to collide with, and a validator that consulted enemy placements would turn `legalPlacementHexes` — the setup UI's highlight overlay — into a third detector, showing the enemy's secret sites as holes in your own legal ground.

31. **The filtered state drops enemy units; it does not mask them** (spec §6, ruled in step 8). `VisibleGameState.units` holds the viewer's own units only, and the entire enemy picture is `intel`, keyed by hex. The tempting alternative — keep enemy units in the array with `kind: 'decoy'` rewritten to `'bunker'` — is a leak wearing a mask: it puts real enemy `UnitId`s into the client, which is the cross-round trackable identity §11 keys every pile of intel by hex to withhold, and it makes `hp` and `kind` into fields the engine has to lie in. As written, `VisibleGameState` has no field an enemy id *could* live in, so the guarantee survives edits by people who have not read this line.

32. **`visibility.ts` decides nothing — if you are computing visibility there, the rule is in the wrong file** (spec §6, §11). `resolve()` owns all the bookkeeping: it files contacts, rebuilds the one-round pile from scratch every resolution, and calls `forgetDestroyed` when a unit dies publicly. `state.intel[playerId]` is therefore *already* exactly what that player knows, and the filter is a projection of it. This is also why the filter is short: it is the boundary, not the brain.

33. **The filter is a projection, not a deep clone, and that is safe only while the render layer keeps its side of the bargain** (CLAUDE.md architecture rule). Arrays are rebuilt so nobody can splice into the real state, but the `Unit` objects inside are shared by reference, because copying every unit on every frame is waste. `src/render/` and `src/ui/` read state and never mutate it — if that rule is ever bent, this is one of the places it goes wrong quietly.

34. **The one visibility guarantee no sim test can protect is that the renderer never sees a raw `GameState`** (closed in step 9). Every leak `visibility.ts` prevents is prevented only for callers that actually call it; handing `GameCanvas` the unfiltered state bypasses the whole layer without failing anything in `src/sim/`. It is now structural: see 35.

35. **`truth` in `src/state/match.ts` is a module-private `let`, and it must stay one** (spec §6). It is deliberately NOT in the Zustand state and has no accessor, so there is no hook, selector, component or test that *can* reach an unfiltered `GameState` — the only way to leak one is to edit that file on purpose. Putting it in the store "for devtools" or exporting a `getTruth()` "just for a test" re-opens the exact hole step 9 was built to close, and nothing would fail when it did. Tests assert through `viewFor`/`logFor`, which is also how the UI reads.

36. **In hotseat one machine holds both players' views and both logs — that is what a pass-the-screen handoff is.** The redaction is `views[viewer]`, so any component reading `views` directly, or a log by a hardcoded player id, silently shows the wrong player their opponent's picture. `useView`/`useLog` key off `viewer` for that reason; add no hook that takes a `PlayerId` from a caller. In V1.5 the same split becomes physical (server keeps `truth`, each client gets its own view) and this class of bug stops being possible.

37. **`hexesInRange` is pure geometry and returns hexes off the edge of the board.** The sim leaves them in on purpose — they can never match a unit, so filtering would cost a map lookup per hex to change nothing (`reconSwath`) — but anything that *draws* from it must filter with `tileAt` or it paints ground that does not exist. This was a live bug in step 9's coverage overlay, found by looking at a screenshot; no test would have caught it. `tileAt` is the only correct on-map test, because the map is a rectangle in col/row and a slanted parallelogram in axial.

38. **Every event the client sees goes through `filterEventsForPlayer`, including the one the store invents.** A resignation is not a board fact, so `resign()` writes `truth` and synthesises the `GAME_OVER` event itself (spec §4) — and then publishes it through the filter like any other, rather than pushing it straight into both logs because it is "obviously public". Who may see an event is §6's judgement and is already written down in one place; a second place that decides it is a second place to get it wrong.

39. **`scripts/soak.ts` holds an unfiltered `GameState`, and that is not a precedent for anything under `src/`** (CLAUDE.md gotchas 34/35). Measuring the game requires ground truth — "did anyone ever find the *real* bunker" is a question no redacted view can answer — so the harness is deliberately outside `src/`, renders nothing, and returns nothing to the client. The part that keeps it honest: **the CPU players inside it are still handed `filterForPlayer` output and nothing else**, exactly as the store hands it to them. The instrument sees through the fog; the players never do. Anything under `src/` reaching for truth is still the hole step 9 closed.

40. **`sweepLanes` runs its lanes edge to edge, NOT inset by the swath radius** (spec §11). Insetting by `reconSwathRadius` is the obvious move and it silently loses the board's outermost column: the swath spreads `radius` columns sideways, but on staggered odd-q columns that spread is a *diagonal*, so a lane at column 1 photographs (0, row) and (0, row+1) while leaving (0, row-1) unseen — and a bunker can legally sit there. Flying the edge itself costs nothing. The test that catches this asserts the whole zone is covered rather than checking lane positions, so a future retune of the radius, the drone's range or the home zone either still covers the zone or fails loudly.

41b. **HOLD is a draft entry that submits nothing, and deleting it breaks the auto-resolve rule, not just a button** (spec §3, §11; added in step 10a). The round resolves the moment every orderable unit is decided — and holding is a legal, often correct order, so without an explicit way to *say* "this launcher stays put" a player who wanted to hold anything could never complete a draft. `draftOrders` strips HOLD before submission, so the engine never learns it exists: a unit it receives no order for holds anyway. The tempting simplification is "just count units with real orders", and it silently deletes holding as a strategy.

41c. **`allDecided` returns false on an EMPTY orderable set, and that guard is why the game does not lock up** (spec §3). During the opponent's dead-hand round you have no orderable units at all, and "every one of zero units is decided" is vacuously true — auto-resolve would fire on an empty draft, resolve, find the same condition, and never stop. A finished match is the same shape. `orderable.length > 0` reads like a defensive nicety and is the opposite.

41d. **Order legality is checked against the `activeSeat`'s view, never the current `viewer`'s** (spec §6; `orderingView` in `match.ts`; step 10a used `SANDBOX_PLAYER`, and step 10c made it the seat — gotcha 55). The viewer switch is a debug control, so a player glancing at the CPU's board must not thereby be drafting orders for the CPU. It needs no ownership check to enforce that: a `VisibleGameState` holds only its owner's units, so an enemy unit id simply is not found. The UI *additionally* disables entry while spectating — two independent guards, one stopping a wrong order being stored and one stopping it being offered, and neither is redundant.

41e. **`modesFor` carries the phase rules that the sim's validators do not know** (spec §3). `validateMove` will happily accept a launcher MOVE during a dead-hand round, because the sim's order validators are phase-blind — §3's "the dead-hand round is launches only, and the opponent issues no orders at all" lives in `modesFor`, and `isLegalOrder` checks it *before* calling the validator. Dropping that guard looks like removing a redundant check and lets a MOVE into a round that has no movement phase.

41. **The soak harness gives the two CPU sides DIFFERENT rng streams.** Seeding both from `seed + round` (which is what `match.ts` does for its single CPU, correctly) hands them identical random sequences — and for EASY, the one tier that actually rolls dice, that makes the two players mirror each other's coin flips and quietly halves the sample. Cross-tier runs play every pairing in **both seats** for the same reason: a seat advantage would otherwise be reported as skill.

42. **`views === null` IS the setup screen — do not add a `stage` field** (added in step 10b). A `GameState` only exists on the far side of `startMatch`, so `truth` is `GameState | null` and both redacted views are null until the human's three assets are down. That one nullable field is the discriminator for the whole client: `App` picks `SetupPanel` or `Hud` from it, `GameCanvas` clears the match layers on it, and `useMatchStarted()` derives a boolean from it. Storing a `stage: 'SETUP' | 'PLAYING'` alongside would look tidier and would be a second fact about the same thing, free to drift out of step with the first. The related discipline: **`useView()` is nullable and must stay so.** The three components that narrow it (`Hud`, `OrderPanel`, `SelectionPanel`) are unreachable with a null view because `App` gates them — the guard is there so the type never has to lie, not because the case happens.

43. **The CPU's setup is generated at MATCH START, not when the map is rolled** (spec §12, step 10b). `beginMatch` calls `cpuSetup` (which is `sandboxSetup` below HARD) at the moment the human finishes placing, which is what makes "the setup screen cannot leak the opponent's placements" structural rather than careful — while you are placing, no enemy setup exists anywhere in the client to leak. Generating both at `newMatch` time would look equivalent and would put the enemy's three secret hexes in the store for the entire duration of the screen whose whole job is to be secret. This is gotcha 30 one level up: the *validator* has no parameter for the enemy's setup, and now neither does the *screen*. **Step 10c must re-establish this deliberately**, because with two humans an enemy setup genuinely will be in the store while the second player places.

44. **Never draw the two players' setups from two identically-seeded rng streams** (step 10b). It is fine to consume one stream sequentially (`scripts/soak.ts`) or to seed two streams differently (`match.ts`, keyed by player so the CPU's board does not depend on whether the human auto-placed). What must not happen is `makeRng(seed)` for both. **And the obvious test for it does not work:** identically-seeded streams do NOT produce mirrored coordinates, because the half-turn maps P1's column-major home-zone list onto P2's *reversed* — so "the two bunkers are not half-turn twins" passes while the bug is live. What they actually produce is both sides taking the **same index of their own legal list**, which lets anyone who knows the algorithm read their own bunker and derive the enemy's. `setupFlow.test.ts` asserts the indices come apart across 12 seeds, because a correct implementation still collides by chance roughly 1 seed in 96.

45. **`sandboxSetup` has exactly one copy, and `scripts/soak.ts` reaches it through `cpuSetup`** (step 10b; `cpuSetup` since 2026-09-27, so each tier sets up in the soak the way it does in a real match). The harness used to carry its own randomised walk because the fixture placed at fixed fractions and would have measured how well the CPU finds one spot rather than how well it searches; once the fixture became seeded-random the two were the same function. If a future change makes the fixture predictable again, the harness needs its own copy back *and* the comment explaining why — but check first, because a predictable fixture is also what makes the human's bunker hunt stop being a hunt.

46. **The ≥3 exclusion is a constraint on a PAIR, and must be checked from both sides** (spec §12, changed 2026-08-13). `validatePlacement` rejects a base placed near a site *and* a site placed near a base — `isSite(p.kind) !== isSite(kind)`. Checking it only from the base's side is what forced the old enforced placement order, because a base put down first had nothing to measure against and passed vacuously; restore that asymmetry and free placement order silently lets an unplayable board through to `startMatch`. The reason code is `EXCLUSION_ZONE` rather than `TOO_CLOSE_TO_SITE` for the same reason, and it still never says which asset was too close — §12's indistinguishability principle governs error messages too, or "the site you may build beside your base" would be provably the decoy.

47. **`PLACEMENT_ORDER` is the roster's canonical order, NOT a sequence anyone must follow** (spec §12, since 2026-08-13). It has exactly two jobs now, both structural: it is the order `startingUnits` adds placements to `GameState.units` — which §9 makes the log's order, so it has to be a function of the *setup* rather than of the clicks that built it — and it is the order the setup panel lists the roster slots in. Deleting the sort in `startingUnits` looks like removing a no-op and makes two players who built the same board in different sequences produce differently-ordered logs from an identical position.

48. **The setup draft is slot-addressed, and `PlayerSetup` is not** (step 10b). `PlacementDraft` is fixed-length with a null per empty slot, because the player picks *which* asset they are positioning and expects it to land on that row — a bare list of placements can only answer "which base is this" by counting from the front, so selecting "base 2" first would fill base 1's row. `placementSetup` converts to the sim's shape at the end, once the distinction stops mattering. Two consequences that look like details: **`placed.length` is always the roster size**, so any counter must count filled slots (this shipped as a "4 / 4" on an empty board), and **`others()` must drop the selected slot's own placement** before validating, or an asset blocks its own relocation.

49. **Committing the setup is explicit; completing the order draft is not** (spec §3, §12). The last placement does NOT start the match, though the last order decision does resolve the round. That asymmetry is deliberate and was a reversal: auto-start was right while placement was a fixed sequence, and wrong the moment any asset could be repositioned, because it takes the board away exactly when the player finally has the whole thing in front of them to judge. Do not "restore the symmetry" — the two screens stopped being the same shape when placement order became free.

50. **`MARCH_DETECTED` is emitted in ascending ORIGIN HEX order, never `GameState.units` order** (spec §9, §11; added 2026-08-13). It is the only **public** event phase 5 emits — `UNIT_MOVED` and `MOVE_FAILED` beside it are owner-only, and they correctly use units order per gotcha 14. Copying that ordering onto the public one is the natural-looking edit and it leaks: two marches in a round would tell the enemy which of two launcher ids sorts first, and a few such rounds reconstruct the ordering of all three, which is the cross-round trackable identity §11 keys every pile of intel by hex to withhold. It is gotcha 22's leak exactly, in a new place, and it uses the same `compareHex`. The general rule, now in §9: **owner-only events may be ordered by units; public ones must be ordered by something already public.**

51. **The forced-march reveal fires on the ATTEMPT, and `MARCH_DETECTED` carries the origin only** (spec §9, §11). Two rules, both easy to "tidy" into a bug. (a) A march blocked by an unseen enemy, or one that loses a standoff, is **still heard** — the boundary is "any march that had an effect on the round", which is deliberately the *same* boundary `MOVE_FAILED` uses (gotcha 13), because both answer "did hidden information cause this?". Gating the reveal on `check.legal` looks like a cleanup and silently makes a blocked march free. (b) The event has **no destination field** and must never grow one: publishing where the launcher arrived hands over its current position, which is the entire thing the price is paid to withhold. What makes the trade fair is that **a launch contact is a target and a march contact is a bearing** — a launcher that fired could not also move, while one that marched has by definition left.

52. **`modesFor` in `src/state/orders.ts` is the single gate on which orders exist for a HUMAN player** (spec §3). It carries the phase rules the sim's validators do not know (gotcha 41e), and `isLegalOrder` consults it before calling any validator, so anything that bypasses `modesFor` to check legality re-opens that hole. **It gated the forced march shut until 2026-08-14 and is now open** (`['MOVE', 'MARCH', 'LAUNCH']`); MARCH stays out of the dead-hand list for the same reason MOVE does — that round runs phases 2→3 and has no movement phase at all, so a MARCH there would emit a public `MARCH_DETECTED` announcing a relocation that can never happen. **One correction to the note this replaces: `modesFor` never gated the CPU.** `cpu.ts` builds orders and calls `validateMove`/`validateMarch`/`validateLaunch`/`validateFly` directly, never `isLegalOrder`, so what kept the CPU from marching was simply that it constructed no MARCH — verified by mutation, since removing MARCH from `modesFor` fails four tests in `orders.test.ts` and none in `cpu.test.ts`. The two paths are checked by the same *validators*, not by the same gate.

53. **An `if/if/fallthrough` over an order kind is a latent wrong-picture bug; use an exhaustive `switch`** (found 2026-08-14 in `drawPreview`). `drawPreview` tested MOVE, then LAUNCH, then *assumed the remainder was FLY*. Widening `Order` with MARCH therefore routed every march hover into the drone's preview — a launcher drew a flight path and a recon corridor — and **nothing failed**, because a fallthrough is not a case the compiler can see is missing. This is the one place the discriminated-union design did not pay out (CLAUDE.md's forced-march sim entry credits the compiler with finding all 14 break sites; it found 14 of 15). `drawMarker` had the matching hole from the other side: a `switch` with no MARCH case and no exhaustiveness check just drew nothing, so a committed march was invisible on the board. Both are now exhaustive switches, which makes the next order kind a build error instead of a silently wrong overlay.

54. **The march overlay marks the ORIGIN, and must never mark the destination** (spec §9, §11 — gotcha 51(b) restated where it is easy to get wrong). `announcedMark` in `draw.ts` paints the hex the launcher *leaves*, in the enemy's red, because that hex is what `MARCH_DETECTED` publishes. Drawing the same mark on the destination would be a UI that lies about the rule in the player's favour — it would imply the enemy learns where you arrived, which is precisely what the price is paid to withhold. The red is a deliberate inversion of the map's colour language (red is normally *what you have detected of them*); here it is *what they are about to detect of you*, which is the same fact pointed the other way, and it is the only mark on the board that means that.

55. **`activeSeat` and `viewer` are two different facts and must not be merged** (spec §6; added in step 10c). `viewer` is whose redacted picture is *drawn*; `activeSeat` is whose turn it is to *act*. In hotseat they are always equal, which is exactly what makes merging them look like a harmless simplification — and in solo they come apart the instant the debug viewer switch is used (since the 2026-09-28 menu cleanup that switch has no button; `setViewer` is reachable from tests and the console only, and the rule still holds), which is the one case the order builder must refuse to serve (gotcha 41d). `orderingView` reads `activeSeat`; every presentation hook reads `viewer`. Collapsing the two makes "glance at the CPU's board" into "order the CPU's units".

56. **`handoff` is its own field, NOT derived from `viewer !== activeSeat`** (step 10c). The derivation is tempting and wrong: in solo those two legitimately differ for as long as you spectate, and blanking the screen then would break the debug control the sandbox is built around. This is not gotcha 42's duplicate-fact mistake — "someone is walking to the machine" is genuinely independent of "who is looking at it", and only one of the two states means *draw nothing*.

57. **Hotseat secrecy is carried by two rules, and it is weaker than what 10b had** (spec §6, §12; step 10c). Until 10c "the client cannot leak the opponent's setup" was structural — no enemy setup existed in it (gotcha 43). With a second human, both players' setups, drafts and views are in the store at once, necessarily. What holds the line now: (1) **no hook takes a `PlayerId` from a caller** — `usePlaced`, `useDraft`, `useView`, `useLog` all key off `viewer` internally, so the only board a component *can* obtain is the current viewer's; (2) **`viewer` changes only through `takeScreen`**, and while a handoff is pending `App` renders the prompt and nothing else. Adding one convenience hook that takes a player id undoes half of it, and nothing would fail when it did. In V1.5 the split becomes physical and this whole class of bug stops existing.

58. **`App` swaps to the handoff screen; it must never overlay it** (step 10c). A full-screen overlay with the canvas still mounted underneath is one CSS mistake — one `z-index`, one `opacity` transition, one stray `pointer-events` — away from showing the previous player's board to the incoming one. The swap makes "there is nothing behind the prompt" a fact about the component tree. `GameCanvas`'s Pixi teardown is already StrictMode-safe, so the unmount/remount costs nothing.

59. **`nextSeat` must not wrap, and `endTurn` must not resolve on the first player** (spec §3; step 10c). One pass over the human seats is one round of drafting, so running off the end means *everyone has drafted* — the cue to resolve — not that it is p1's go again. And the first player finishing must pass the screen rather than resolve, or their opponent's empty draft gets submitted on their behalf and the first player gets a free round, every round. Orders are simultaneous; the handoff is presentation, and it must not become turn order. Mutation-checked both ways: wrapping fails `seats.test.ts`, resolving early fails 5 tests in `hotseat.test.ts`.

60. **A battle report is never raised for a bunker hit, and that is a hidden-information rule, not a UI preference** (spec §6, §12; V1.1 step 1). `reports.ts` is deliberately near-silent: a confirmed-kill banner fires only for a launcher, plus the outcome banners at match end. Two things break the moment a `BUNKER_HIT` gets one. To the **attacker** it is a bunker detector — blind-fire a spread, watch for the popup, and "only drones find bunkers" is finished, which is the exact leak `IMPACT`'s never-name-a-victim rule exists to prevent. To the **game** it erases the tell the decoy rests on: a real bunker takes a hit *in silence* where a decoy dies loudly, and buying that difference is what the attacker spends a missile on. The negative tests in `reports.test.ts` (`says nothing when a bunker is hit`, and the same for decoy/base/impact) are the guard, and they are not padding — a plausible-looking "make notifications more helpful" change fails them.

61. **`UNIT_DESTROYED` has no `owner`, so "was that mine?" is a roster lookup — and it only works because the filtered roster keeps your own dead** (spec §6; gotchas 21, 31). The event is public and names a `unitId`; adding an owner field to it would be a step toward the cross-round trackable identity §11 keys all intel by hex to withhold. So `reports.ts` and `eventText.ts` both answer the audience question the same way: `ownUnits.some(u => u.id === event.unitId)`, where `ownUnits` comes from a `VisibleGameState` and therefore *cannot* contain an enemy id. The second half is the fragile one — `filterForPlayer` keeps the viewer's own **destroyed** units (your losses are your own knowledge), and if that ever changed, a player would be congratulated with "Confirmed kill" for losing their own launcher. There is a test pinning exactly that.

62. **Banners are mounted inside `App`'s board branch, never above the handoff `if`** (spec §6; gotchas 36, 57, 58). In hotseat both players' news sits in the store at once, so a full-screen "Launcher lost" rendering while the screen is blanked would hand the round to the incoming player before their opponent has stood up. `App` *swaps* to `HandoffScreen` rather than overlaying it, and `<BattleReport />` lives in the other branch — so "no banner during a handoff" is a fact about the component tree, not a z-index promise. The matching state rule: reports are **queued per player** and `dismissReport()` pops the *viewer's* head, taking no `PlayerId` — the absent player's banners wait for them to sit down. Hoisting the component to `App`'s common path to "avoid duplication" re-opens the hole, and nothing in `src/sim/` would fail.

63. **`cpuOrders(view, difficulty, player, rng, history)` — a real match must pass `history`** (2026-09-27). It defaults to `[]` so single-round tests stay short, and that default is exactly how the fix can be silently undone: forget it at a call site and the drone goes back to dying on the same hex, with every test still green. The guard is the soak's repeat-death line, which should read ~0.0 for MEDIUM and HARD. And `history` must be the seat's **filtered** log (`logs[player]`, or `filterEventsForPlayer` output) — handing the CPU the raw log is the gotcha-34 hole in a new place.

64. **A base is exposed by intercepting a MISSILE, never by killing a drone, and `BASE_EXPOSED` is filed on the ENEMY's map** (spec §10, §11; added 2026-09-27). Three things look like harmless tidy-ups and each is a bug. (a) Exposing on drone kills too would make the defender's quiet tool loud and turn every drone death into an exact fix instead of a 19-hex clue. (b) Filing the reveal on `intel[base.owner]` — the base's own side — reads naturally off the unit and is gotcha 21b's trap; nothing a player does writes their own intel. (c) The "already on file" check is the once-per-base rule, not an optimisation: delete it and every later intercept re-announces a base both players already know. The event carries a hex and no unit id, and simultaneous exposures are ordered by hex (§9) — `interceptor.test.ts` pins all of this, including an ordering case where interception order, units order and id order all disagree with hex order.

65. **Missiles outlive the round, and three rules keep that honest** (spec §3, §4, §10; added 2026-09-27). (a) **The dead-hand `while (working.missiles.length > 0)` loop is not a safety net** — without it a range-5–6 retaliation is fired in a round whose own verdict freezes it, and the decapitated player's longest shots silently cannot matter. (b) **`isDisarmed` reads `state.missiles`**; dropping that line looks like a tidy "launchers only" reading of §4 and voids a winning missile whose launcher died under it. (c) **A carried missile's current hex is never re-checked** — `flyMissiles` starts from `path[traveled]`, the next *unentered* hex; starting from `traveled - 1` "to be safe" double-engages a missile parked in a bubble. And `VisibleMissile` is built field by field, never `{ ...m }`: a spread carries `launcherId` to the enemy. `flight.test.ts` pins all four.

66. **`cpuSetup` flips the bunker/decoy coin LAST, and scores bases by a function symmetric in the two sites** (spec §12; added 2026-09-27). The base goes public on its first intercept (`BASE_EXPOSED`), so any correlation between the base and *which* site is real is a tell. The natural code does exactly that: pick the bunker, then the decoy, then the base "covering the bunker". The placer instead never knows the answer until the base is down. Both leaks were mutation-checked: scoring by the bunker's lanes fails `HARD’s base is no nearer the bunker than the decoy`, with the coin first or last. Two smaller rules: **Auto-place must stay on `sandboxSetup`** (routing it through `cpuSetup` fails `setupFlow.test.ts`), and **the gap cap must never ship without the scored base** (on its own it loses 43–48).

67. **Every CPU "can I shoot that?" goes through `canFire`, and a blocked shot is never *rejected* — it silently becomes a move** (spec §10; added 2026-09-28). Since line of fire, `distance <= missileRange` is only half of "can fire", and a bare range filter anywhere in `cpu.ts` looks correct and is a bug. `canFire` (range, not own hex, `lineOfFireClear`) is the one place the CPU asks. `validateLaunch` stays the final word on every order, so the CPU never *submits* a `LINE_BLOCKED` launch; an unfiltered target makes `reactiveLauncherOrder` fall through to a ground move instead, which is invisible in every test that only checks legality. That is why the soak's `LINE_BLOCKED launches sent` line should read 0.00 (an honesty check) and why the line that actually shows lane-blindness is **launcher-rounds with a site in range but no clear line**. HARD's `site` goal (`siteGoal`) scores the distance to the nearest clear firing hex from `firingPositions`, the same enumeration the generator and `approachLanes` use; `dangerHexes` counts only hexes a contact has a clear line to. The UI side is the same trap: `launchTargets` must filter by `lineOfFireClear`, and `orders.test.ts`'s "every target the UI offers is accepted" test is what caught it when the session brief assumed it came free.

68. **A replay is keyed per player and cleared only for the viewer, and it plays only inside the mounted canvas** (presentation Session 1; gotchas 36, 57, 58, 62). `MatchState.replay` holds one pending replay per seat, and `finishReplay()` takes no `PlayerId` — in hotseat P2's replay must survive P1 watching or skipping theirs, and a skip that could name a player would let the person at the machine consume the other seat's. Nothing plays during a handoff because `App` unmounts `GameCanvas` (and with it the ticker function); moving playback into a component that stays mounted, or a timer outside the canvas, re-opens that. Two more rules: a replay's `events` must stay the same filtered slice the log receives (`publish` builds both from `seen`), and `buildTimeline` must never sort — it relies on §6's phase-ordered log, which `replay.test.ts` checks on real rounds. All four were mutation-checked.

69. **An impact is drawn from its hex and the clock, and nothing else** (spec §6; gotcha 60; presentation Session 2). `impactBlast(g, x, y, q)` in `playbackDraw.ts` has no parameter that could say what was on the hex, so an impact on a bunker, a decoy, a launcher or bare ground is one picture. What the viewer learns about the hit comes afterwards, only from damage events they are allowed to receive. Two tempting edits break this: sizing or colouring the blast from the next `UNIT_DESTROYED`/`BUNKER_HIT` ("make kills feel bigger"), or peeking ahead in the event list inside the impact clip. Either one turns the explosion into the bunker detector `IMPACT`'s design exists to prevent. `flights.test.ts` pins that an impact's plan is identical with or without a following kill. The missile's *flight* (its colour, whether it dives first) may vary, because that comes from the launch, which is public. Also: `planFlights` must never read a launcher id, and whose missile it is comes only from its origin (`LAUNCH_DETECTED`) or `VisibleMissile.owner`.

70. **The intel overlay and the CPU share ONE inference, and the overlay holds back the round being replayed** (presentation Session 3; gotchas 57, 63, 68). `enemyBaseCandidates` in `src/state/inference.ts` is what `droneDangerHexes` flies around and what the board shades red. Copying it into the render layer "to keep drawing code self-contained", or tuning one copy, makes the human and the CPU see different deductions from the same log, and nothing would fail. Two more rules: (a) `intelOverlay` draws a pending replay's `from` board with that round's log entries removed, exactly as `EventLog` does. Drop the filter and the settled shading appears under the replay before the drone is shown going down (`holds back the round being replayed` fails). (b) The prunes are **sound, never generous**: a candidate is removed only for what the viewer provably knows (off the board, outside the enemy home zone, within R of a hex our drone *transmitted* from). Pruning by the photographed swath instead of the transmitted path looks equivalent and removes the real base; the real-match soundness test catches it.

71. **The how-to-play screen types no number and may promise nothing the rules do not give** (presentation Session 4; gotchas 58, 60, 62). `helpContent.ts` builds every number from `RULES`/`UNIT_DEFS`/`SPAWNS`, and `helpContent.test.ts` fails on any digit in the copy that is not one of those values. It also fails if any sentence mentions dodging without saying it cannot be done (a warned missile lands before anyone moves), if a sentence about a bunker hit mentions an alert, banner or warning (the attacker's silence *is* the decoy test), on a plural "bases" while each side has one, or on a "§". The window is mounted in `App`'s board branch next to `BattleReport`, never above the handoff `if`, and `App` closes it when a handoff starts. It swallows Space/Enter/Escape in the **capture** phase so Esc closes it without also skipping the replay or dismissing a battle report. And `HowToPlay.tsx` + `helpContent.ts` are deliberately not `HowToPlay.tsx` + `howToPlay.ts`: names differing only in case break the build on macOS and Windows.

72. **Every unit emblem comes from `EMBLEM` in `src/render/emblems.ts`, and from a piece's kind alone** (unit-emblems session; gotchas 31, 69, 71). Four rules keep it honest. (a) `emblemAt(kind, …)` takes no hit points, event or unit, so a wreck, a hit bunker or a kill can never change a shape; sizing or tinting one from damage re-opens gotcha 69's detector. (b) There is a `'decoy'` emblem, but enemy intel is typed `MaskedStaticKind`/`SpottedKind`, which have no `'decoy'`, so an enemy site can only be drawn as a bunker. Never widen those to `UnitKind` "to simplify" a call. `legend.test.ts` pins the same for the key. (c) **Shapes within one emblem may touch but never overlap:** Pixi applies a Graphics' alpha shape by shape, so an overlap shows as a darker patch on a faint contact or a wreck. A hole must lie wholly inside its shape, or `cut()` fails silently. `emblems.test.ts` checks both by sampling. (d) `emblems.ts` imports only types. The UI reads it for the legend, and one Pixi import would drag the renderer into `src/ui/`. Board and legend draw the same list: never give the legend its own copy of a shape.

73. **The end-of-match reveal is the one piece of `truth` that reaches the store, and only at `GAME_OVER`** (final-reveal session; gotchas 34, 35, 36; spec §6). `MatchState.finalReveal` holds each player's opponent's units straight from `truth`, decoy included, set only in `publish` via `finalRevealOf`, which returns null unless the phase is `GAME_OVER`. That guard is the whole safety of the feature: dropping it hands the renderer the enemy's positions all match (`finalReveal.test.ts` "does not exist while the match is being played" fails). It is keyed by viewer and read only through `useFinalReveal` (gotcha 36). It lives in `publish` so both endings, the engine's verdict and `resign`, get it with no special case. `src/sim/` is untouched: `filterForPlayer` still drops enemy units, and must keep doing so. The board draws it with `drawReveal` on the intel layer *instead of* intel and the base-candidate shading, and only after the final replay has played, so the reveal never spoils the round that ended the match.

### Open questions
- **SETTLED 2026-08-12: no partial advance. §9 stands exactly as written — a blocked move fails entirely and the launcher holds.** Raised as "stopping at the last open hex so the round isn't wasted", explored, and withdrawn on the reasoning §9 already gives: **advancing into unscouted ground has to risk something, and that risk is what makes the drone worth flying.** Three things a future session should know before re-opening it. (1) **There is no path in this engine.** `reachableHexes` is a flood fill that treats occupied hexes as walls, so an enemy *between* you and your destination is routed around invisibly and costs nothing. A move is wasted in only two cases: you ordered the launcher **onto** a hidden unit's hex, or (rarely, in a chokepoint) an unseen blocker cut every route within budget. It is not "I bumped into something on the way" — that cannot happen. (2) **Walk-and-stop would need a canonical path** plus an equal-cost-route tiebreak, a UI path preview, and both reproduced identically on the V1.5 server — and it would let one order probe a whole lane and name the exact hex that stopped it, a bunker-finding detector competing directly with the drone (§11, §12). (3) A pathless variant (land on the reachable hex nearest the destination) leaks nothing new and was the option on the table, but it makes probing **cheap**, which is the same objection in weaker form: today driving at a suspected hex costs a full round when you are right. If playtest shows the wasted round is merely annoying rather than tense, that variant is the first thing to try — and standoffs would have to fall back identically, or a partial advance becomes a free tell that an enemy moved at you (gotcha 13).
