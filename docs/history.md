# Nuke Wars — build history

Everything that has been built, one entry per session, oldest first. Moved here from the "Current status" section of `CLAUDE.md` on 2026-09-29 (V1.5 Session 1) so that file stays short enough to read at the start of every session.

**This is a record, not a to-do list.** The live state of the project — what is next, open questions, known issues and the load-bearing gotchas — stays in `CLAUDE.md`. Entries are kept as written at the time, so older ones may describe code that has since changed; where an entry and the code disagree, the code and `CLAUDE.md` win. Gotcha numbers cited below refer to the list in `CLAUDE.md`.

New entries go at the bottom, dated, in the same style.

- 2026-08-11: **map axis corrected to north/south.** Territory was split left/right (19w × 15t, mirrored columns); it is now split top/bottom — **P1 holds the south and advances north**, P2 holds the north. Map is **16 wide × 19 tall**. - 2026-08-11: **terrain simplified to two types (`feature/terrain-tiles`).** `urban` is **cut** (flavour-only, no rule; its V2 regime-score role is flagged in `v2-backlog.md`). `Terrain` is now `'plains' | 'mountain'`. Mountains went from ~14% scattered singletons to **15% grown as ranges** — 4 per generated half, walked with a 0.7 straightness bias, then a de-orphaning pass that relocates any lone mountain against an existing range, so "every mountain touches another" is a guaranteed property and not a tendency. Because ridges (unlike noise) can wall a board off, `generateMap` is now **generate → validate → re-roll**: coverage inside 10–20%, all 8 spawns in one connected plains region, and no launcher more than 12 ground-cost from a firing position on the enemy line (8 on open ground — this is the §7 "first blood ~round 3" premise made testable). Re-roll rather than carve, because an asymmetric carve breaks the half-turn. Spawn hexes *and their rings* are now excluded from mountain seeding up front, rather than converted to plains afterwards. **Rules change: bunker, decoy and interceptor bases may be built on mountains**; launchers and drones still spawn and move on plains only. `TerrainDef.passable` → `groundPassable` and new `RULES.placementTerrain` — the rename exists so placement code cannot silently reuse the movement flag. New `defs.test.ts` asserts bunker and decoy allow identical terrain (§12) and that HP is their only difference; `movement.test.ts` cross-checks the new `groundCostsFrom` in `map.ts` against `reachableHexes` so the two flood fills can't drift. Spec §2/§7/§10/§11/§12 + ledger amended. 116 tests passing.

Everything that leaves that file has been through `filterForPlayer`/`filterEventsForPlayer`, including the `GAME_OVER` event the store synthesises for a resignation.

- 2026-08-13: **CPU opponent, three difficulties (`feature/cpu-opponent`).** Not a build-order step — a solo-play/testing feature requested outside the numbered sequence. New `src/state/cpu.ts`: `cpuOrders(view, difficulty, player, rng)` decides one round's `Order[]` from that player's own `VisibleGameState` alone — never `truth` — so the CPU is bound by exactly the fog a human in its seat would be. It turns its redacted view back into a `GameState`-shaped "belief" (own units only, nothing standing in for the enemy) and checks every proposed order against the real `validateMove`/`validateLaunch`/`validateFly` before returning it — one concrete answer to the "UI only has a VisibleGameState" open question step 9 left for step 10, applied to the CPU first since it needed no UI to ship. EASY mostly holds/hovers and ignores intel; MEDIUM advances toward the enemy's home zone and fires at the nearest known target, kind-blind; HARD prefers a launcher contact over a bunker/decoy site when both are in range (a contact is a certain kill this round, §11) and prefers a safe reachable hex over a barely-better exposed one. All three are fully stateless — nothing is remembered between rounds. `resolveRound()` in `match.ts` now calls `cpuOrders` for `SANDBOX_DUMMY` instead of submitting `[]`; a `difficulty` field + `setDifficulty` joined the store, with three buttons in the HUD. 27 new tests (`cpu.test.ts`): legality checked against TRUE state at match start (not just belief), the `ordersPerUnit` invariant, determinism, MEDIUM/HARD target-priority divergence, HARD's movement-safety tolerance, and an illegal-order-avoidance case (degenerate intel that would resolve to a same-hex LAUNCH). 436 tests passing.
  - **Dead hand gets its own targeting, not `knownTargets`'s.** `adjudicate()` checks bunker outcomes before it ever reads a launcher count (`outcomes.ts`), so a launcher-contact kill during the final volley cannot change the verdict — only a hit on the enemy's real bunker can (Mutual Annihilation instead of losing outright). `deadHandOrders` targets known bunker/decoy sites only and blind-fires into the opponent's home zone otherwise; it never aims at a contact.
  - **A design bug caught before it shipped, not after:** the first draft ranked HARD's targets with a *stable* sort over an array where contacts were already pushed before static reveals, so the sort was a no-op and MEDIUM would have "preferred" contacts by sheer accident of insertion order — no actual behavioural difference between the two tiers. Fixed by making MEDIUM's selection distance-only (kind-blind) and HARD's priority-first, distance-tiebreak (`selectTarget`, both exported and unit-tested directly).
  - **Headless soak test, run and then deleted (not shipped):** 180 full CPU-vs-CPU matches through the real `resolve()` loop (20 seeds × all 9 difficulty pairings) — zero thrown errors, zero infinite loops. Found and worth flagging, not fixed this session: **zero DECAPITATION or MUTUAL_ANNIHILATION outcomes across all 180 matches** (128 Armistice, 44 Disarmament, 8 Mutual Disarmament). The drone heuristic (MEDIUM/HARD) always advances straight toward the front rather than sweeping side to side, so it essentially never explores enough of the enemy home zone's width to spot a bunker site — the CPU can play a whole match without ever attempting the bluff-test mechanic that is half the game. Not a bug (it does exactly what's documented); a tuning gap worth a follow-up session if CPU matches should exercise decapitation too. **→ Closed the same day — see the next entry. The soak was rebuilt as a committed tool rather than a throwaway, and the cause turned out to be two defects rather than the one guessed at here.**

- 2026-08-13: **balance harness + the CPU actually plays the game (`feature/cpu-bunker-hunt`).** Follow-up to the same day's CPU session, closing the decapitation gap it flagged. New `scripts/soak.ts` + `vitest.soak.config.ts` + `npm run soak`: plays whole CPU-vs-CPU matches through the real `resolve()` loop and reports outcomes, recon coverage, and offense — the measurement tool the last session wrote, used once, and deleted. It runs under Vitest because there is no TS script runner and adding one would be a new dependency; the separate config is what keeps `npm test` fast and the harness out of it. 448 tests passing (12 new); all four new invariants mutation-checked. No sim, spec or rules changes — this session is entirely `src/state/` and tooling.
  - **The gap was two defects, not one, and the harness named both.** (1) `advanceRow` was serving as the drone's goal as well as the launcher's, and it returns the *near* edge of the enemy home zone — so the drone flew to the boundary on round 2 and re-photographed one corridor for the rest of the match, covering **13%** of the zone it was supposed to be searching, and never flying deep enough to enter an interceptor bubble (0 drone deaths at medium/hard, so §11's "bases are inferred from `DRONE_DOWNED`" never fired either). (2) Even the 17/40 sides that *did* find a site never prosecuted it: launchers pushed at a generic row and HARD's targeting preferred a launcher contact over the site.
  - **Fixes.** `sweepLanes` + `nextSweepWaypoint`: a serpentine tour of the enemy home zone, derived from `RULES` rather than written down, that MEDIUM and HARD both fly — recon is not a difficulty setting, a drone that does not search is just broken. HARD's launchers now drive to within missile range of a known site (`AdvanceGoal`), and HARD's target ranking was **reversed** so a site outranks a contact.
  - **Result, measured over 100 matches per pairing.** Hard mirror: decapitations **0 → 45**, mean match length **22.1 → 15.3 rounds**, zone photographed **13% → 26%**, hits on the real bunker **0.10 → 0.45**. The game now reaches its own endgame instead of timing out.
  - **Head-to-head was added because the mirror numbers could not answer "is HARD actually harder?"** — and the first answer was no: hard vs medium came out **50–50**. That is what motivated the target-ranking flip (a HARD launcher that drove across the board to reach a site and then shot a passing contact had wasted the whole maneuver), which moved it to **58–49**. medium beats easy 133–0, hard beats easy 138–0.
  - **The harness holds an unfiltered `GameState` and that is not a licence** — see gotcha 39. The CPU players inside it are still handed `filterForPlayer` output and nothing else.

- 2026-08-13: **build-order step 10a — the order builder DONE (`feature/order-builder`).** The first of step 10's three sessions. **The game is now playable by a human**: you select one of your units, choose what it does, see the consequence drawn on the board, and the round resolves. Until now `resolveRound()` submitted `[]` for the human side every round, so the game was a spectator view of a CPU playing alone. New `src/state/belief.ts` and `src/state/orders.ts`, a new `orders` layer in `src/render/draw.ts`, and `src/ui/OrderPanel.tsx`. 496 tests passing (48 new); both required invariants mutation-checked. No sim, spec or rules changes — this session is entirely `src/state/`, `src/render/` and `src/ui/`.
  - **`belief.ts` is the lift, and it was proven inert before anything was built on it.** `believedState` and `knownEnemyHexes` moved out of `cpu.ts` verbatim; `cpu.test.ts` stayed green with **zero edits** and `SOAK_SEED=7 npm run soak` printed **byte-identical** numbers before and after. That pair is a stronger guarantee than any test written for the refactor, because it runs the real CPU through the real `resolve()` loop. The property it buys is worth naming: **the CPU and the human are now checked by the same import**, so "the CPU is bound by exactly the fog a human faces" is structural rather than a promise.
  - **The step-9 open question is answered.** "The validators take a `GameState` and the UI only has a `VisibleGameState`" is solved by belief, not by narrowing the sim — `moveTargets`/`launchTargets`/`flyTargets` each defer to the real `reachableHexes`/`validateMove`/`validateLaunch`/`validateFly`, and this session hand-rolled no legality anywhere. Narrowing the validators to `(units, map)` remains available as its own housekeeping session.
  - **Orders resolve themselves once every orderable unit is decided** — requested mid-session, and it forced a real design addition rather than a counter. Holding is a legal and often correct order (§3: a launcher with no order holds; §11: hovering is "a real choice, not a wasted round"), so "all orders submitted" could not mean "all four units have a MOVE/LAUNCH/FLY" — a player who deliberately held anything could never complete a draft. Hence `HoldEntry`: a decision that **submits nothing** and exists solely to make "I am finished with this unit" expressible. `draftOrders` strips it, so the engine never learns it exists. The manual **Resolve round** button stays, for going early with units left holding.
  - **`allDecided`'s `length > 0` guard is the one that would have bitten.** During the CPU's dead-hand round the human has zero orderable units, and "every one of zero units is decided" is vacuously true — without the guard the round would have resolved itself instantly and forever. The same guard covers a finished match.
  - **`resolveRound()` lost its `orders` parameter** and reads the draft instead; keeping both would have given the round two sources of truth. The three `match.test.ts` call sites migrated to `setOrder(order)` + `resolveRound()`, which is the better test — it exercises the path a click actually takes.
  - **Not built, deliberately:** setup placement (10b), hotseat handoff (10c), and animation from the event log. `sandbox.ts` still invents both setups.

- 2026-08-13: **build-order step 10b — the setup placement UI DONE (`feature/setup-placement`).** The second of step 10's three sessions. **The match now starts from a board you built:** you hide your bunker and decoy, place two interceptor bases outside both exclusion rings, and the match begins the moment the fourth asset is down. New `src/state/placement.ts` and `src/ui/SetupPanel.tsx`, a `nextPlacementKind` in `src/sim/setup.ts`, a `placement` layer in `src/render/`, and a rewritten `sandbox.ts`. 550 tests passing (54 new); all eight new invariants mutation-checked. Verified in a real browser, not only in tests — placing, illegal clicks ignored, exclusion wash appearing on cue, the setup→match→setup round trip clean with no stale layers and no console errors.
  - **The store no longer opens on a match, and that is the structural part.** `truth` was a module-private `GameState` initialised at module load; it is now `GameState | null`, because a `GameState` only exists on the far side of `startMatch` and inventing a half-built one in the client is exactly what this layer must never do. `views` went nullable with it and **is the setup screen's only discriminator** — `views === null` *is* "still placing". A separate `stage` field was considered and rejected: it would be a second fact that could disagree with the first.
  - **The setup screen cannot leak the opponent's placements, because they do not exist yet.** `beginMatch` generates the CPU's setup at match start rather than when the map was rolled, so while the human is placing there is nothing in the client to leak — no filter involved and nothing to get wrong.   - **The math:** the world point under the cursor is `(p − pos) / scale`; the new position is `p − world × newScale`. At a `ZOOM` limit `zoomAt` returns the same camera object, so nothing moves while the wheel turns against the stop.

A mouse notch is ~13% (was a fixed 10%). A trackpad sends many tiny deltas, so a fixed step per event made it lurch; now it glides. Two-finger scroll zooms too, rather than panning: a wheel event cannot reliably say whether it came from a mouse or a trackpad, and turning scroll into pan would take zoom away from mouse users.
